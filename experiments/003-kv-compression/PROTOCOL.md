# First experiment protocol — 2026-10-20

Status: written before collecting results. This is an infrastructure and feasibility baseline, not a new compression algorithm.

Question: does a packed low-bit KV cache preserve exact retrieval from long documents, and how do stored bytes, peak memory, prefill time, and decode time change?

Model: Qwen/Qwen3-4B, immutable revision recorded in model manifest. BF16 weights and activations, PyTorch SDPA, single RTX 3090, no weight quantization, no training. Disable TF32 and thinking. Published Hugging Face HQQ quantized-cache baseline: 2 and 4 bits, group size 64, axes 1/1, residual length 128; compare DynamicCache BF16. This is not a faithful KIVI or TurboQuant reproduction and has no fused packed-cache attention kernel.

Twelve paired synthetic prompts: 4,096 and 16,384 input tokens; target record at 10%, 50%, 90% of document; two seeds. Distractors contain other numeric codes. All methods receive identical token IDs. Document prefill excludes a final 64-token suffix containing the question, so answering requires reading compressed historical KV. Greedy generate 32 tokens, including any tokens after EOS solely to hold timing work constant. Score the first six-digit answer before the first EOS against the target. Retain all answers and timings. Fixed generation length measures a controlled workload, not user-visible completion latency.

Record synchronized wall times for document prefill, question suffix, and 31 subsequent decode steps (the question produces the first output token). Record actual cache tensor storage including quantizer scales/zero points, full-precision residuals, and backing-storage padding, deduplicated by storage pointer; exclude Python/CPU metadata, model weights, and scratch from this cache-only metric. Separately record whole-process PyTorch allocated GPU memory and peak allocated GPU memory from each phase. CUDA reservation, driver overhead, and other processes are separate from allocated memory. Record representative first-layer tensor layout for audit.

Warm up every method on a short prompt before the recorded sweep. Rotate method order across cases. Fresh cache per case. No latency claims about serving concurrency or optimized engines. No confidence claim from twelve easy synthetic questions; outcomes establish implementation behavior and motivate a broader held-out task suite. Checkpoint hashes, package versions, seeds, prompts, raw JSONL, and source accompany report.

Amendment after one 4K middle-position smoke case, before the 12-case recorded sweep: use common BF16 document prefill in chunks of 2,048 tokens for every method, then convert each layer once at the document boundary for HQQ. Charge conversion time and peak memory to prefill and also report conversion time separately. The smoke run used a single document forward; its results stay separate. This bounds long-prefill activation scratch and avoids repeated requantization during chunked document loading. Compression remains active throughout question processing and generation. The first experiment therefore measures compression at a stable document boundary, not an always-quantized prefill implementation. It temporarily retains the BF16 document cache during ingestion; savings in final cache do not imply that a longer document can be ingested in this implementation. No quality threshold or prompt was changed after the smoke.

Decision: do not call this acceleration unless end-to-end latency or SLO-qualified serving throughput improves at matched quality. Cache compression alone is a storage result. Next experiments need an optimized packed-cache attention path, FP8 where supported, strong rotation/codebook baselines, multi-turn retrieval/code tasks, and concurrency sweeps. Any new allocation policy must beat equal-byte fixed precision and strong existing mixed-precision methods on held-out workloads.

Exploratory extension after the main sweep: run HQQ8 with identical parameters and all 12 original prompts, recorded separately as raw_diagnostic8.jsonl. Motivation: distinguish aggressive low-bit corruption from a pipeline that fails at any compressed precision. This is post-hoc and shares prompts with the main sweep; it is not an independent confirmation set. No changes to prompts or quantizer settings are selected from its answers. Timing is from a separate sequential run, outside the rotated main comparison.
